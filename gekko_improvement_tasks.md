- [x] **Size NO positions smaller than YES at equivalent prices** — reframed as **payoff-skew sizing** in Gordon. The bot only ever holds long-YES positions ("SELL" = exit, not "buy NO"), so there's no YES/NO field to key on — but the *asymmetry the task describes is real at the price level*: a YES bought at 0.60 risks 0.60 to make 0.40. `entrySkewSizeMult` (`gordon/signals.go`) scales BUY size by reward:risk `(1−p)/p`, capped at 1.0 so entries ≤0.50 are untouched and richer ones shrink toward `ENTRY_SKEW_FLOOR` (0.30); `MAX_ENTRY_PRICE` (0.70) refuses BUYs above the ceiling. ## 🔴 Polymarket execution overhaul (added 2026-07-11, from `polymarket_lp_tool` review)

> **2026-10-15: all eight order-path defects below are fixed** in `broker-worker/polymarket.go` and covered by `polymarket_test.go`: the EIP-712 digest and signature match Polymarket's own golden vectors (python-order-utils `test_order_builder.py`, both the CTF and neg-risk exchanges), the L2 HMAC matches py-clob-client's `test_hmac.py` vector, amounts follow py-clob-client's tick rounding, and the CLOB reply is parsed so success needs `success=true` plus an `orderID`. Token ids come from the `POLY-<token id>` ticker; tick size and neg-risk are looked up per token. New env: `POLYMARKET_API_KEY` / `POLYMARKET_API_SECRET` / `POLYMARKET_API_PASSPHRASE`. **Never run against the live CLOB**: no real order has been submitted, and it stays unproven against the live API until a small real order fills. Still open: the lifecycle items (fill confirmation, cancel, error failsafe) and everything below.

_Findings from comparing `broker-worker/polymarket.go` against a working CLOB implementation ([lihanyu81/polymarket_lp_tool](https://github.com/lihanyu81/polymarket_lp_tool), esp. `rust_mm_bot/src/polymarket_api.rs`). Bottom line: **gekko's live Polymarket path could never fill a real order** — and worse, it can report `Success: true` on failure. Item 1 blocks everything else. First step: audit the ledger for any live-mode Polymarket "fills" recorded to date; they are almost certainly phantom._

### Critical — `ExecutePolymarket` is broken end-to-end (`broker-worker/polymarket.go`)

- [x] **Fabricated token ID** — `tokenID = keccak256(intent.ContractID)`. Real CLOB token IDs come from Gamma's `clobTokenIds`, which `marketdata/polymarket.go` already parses (`parseYesToken`) and stores in `p.token`, but the mapping never reaches broker-worker. Orders target a nonexistent ERC-1155 token. Fix: carry the real token id through `TradeIntent` (marketdata already keys tickers as `POLY-<yesToken>` — extract from the ticker or add a field).
- [x] **No L2 auth headers** — `POST /order` requires HMAC-signed headers (`POLY_ADDRESS`, `POLY_SIGNATURE`, `POLY_TIMESTAMP`, `POLY_API_KEY`, `POLY_PASSPHRASE`); gekko sends none → 401 before anything else matters. Needs the API-key derivation/creation flow plus per-request HMAC-SHA256 over `timestamp+method+path+body`. Reference: `polymarket_api.rs::l2_headers`. New env: `POLYMARKET_API_KEY` / `POLYMARKET_API_SECRET` / `POLYMARKET_API_PASSPHRASE`.
- [x] **Wrong EIP-712 domain + contract** — domain name is `"ClobExchange"`; real is `"Polymarket CTF Exchange"`. Verifying contract `0x4b50b11d1e4c759495b45283f5104a806013a52e` is not the CTF Exchange (`0x4bFb41d5B3570DeFd03C39a9A4D8dE6Bd8B8982E`), and there is no neg-risk handling (neg-risk markets sign against a different exchange contract, `0xC5d563A36AE78145C45a50134d48A1215220f80a` — LP tool looks up `neg_risk` per token and switches).
- [x] **Order struct hash omits `signer`** — the real Order type is `Order(uint256 salt,address maker,address signer,address taker,...)`; gekko's typehash and struct hash drop the `signer` field, so the signature can never verify.
- [x] **maker/taker amounts inverted for BUY** — for BUY the maker gives USDC (`price×size`) and takes tokens (`size`); `computeEIP712OrderHash` has it backwards (swaps only for SELL).
- [x] **Wrong request payload shape** — sends `price`/`size` + integer `side`; the API expects `makerAmount`/`takerAmount` strings, `side` as `"BUY"`/`"SELL"`, and `signatureType` inside the order object. No tick-size lookup or decimal rounding either — amounts must be rounded per tick regime (see `polymarket_api.rs::compute_order_amounts` + `get_tick_size`).
- [x] **Failure masking** — when the response lacks `orderID`, gekko fabricates a `BrokerTxID` from the sig hash and returns `Success: true`; breen's ledger then records fills that never happened. Also treats any HTTP 200 as success without checking the body's error fields. Fix: success **only** on a real `orderID`; propagate the CLOB error message otherwise.
- [x] **Salt reuses the time-seeded-RNG hazard** already flagged for gordon in `bug_list.md` — two concurrent orders in the same nanosecond collide. LP tool derives salt from ms-timestamp + pid; anything non-time-seeded works.

### 🟠 High — order lifecycle management (currently fire-and-forget)

> **2026-10-15, Polymarket only:** after a POST the broker polls `GET /data/order/{id}` for up to `POLYMARKET_FILL_WAIT` (8s), cancels any unfilled remainder with `DELETE /order`, and returns the confirmed `filled_size`; breen books only that (`liveFill`), and an unfilled order is a failure, so nothing is booked. After `POLYMARKET_MAX_API_ERRORS` (5) consecutive network/5xx/401 errors the broker refuses new orders until restarted. Tested against a scripted fake exchange only. **Still open:** the booked price is the order's limit price (an upper bound for a BUY; the true average needs `/data/trades`), startup reconciliation of open orders and positions, the user WebSocket, and the same lifecycle for **Kalshi** (which still books the proposal size).

- [x] **Fill confirmation + reconciliation** — broker-worker submits a GTC order and returns immediately; nothing ever checks whether it filled, partially filled, or is still resting. Breen books the trade as if filled at `MaxPrice`. Add: poll `GET /order/<id>` (or user WS, below) after submit; report actual filled size/price back; reconcile open orders on startup.
- [x] **Cancel support** — no cancel endpoint exists anywhere in gekko. Needed for unfilled resting orders, force-exit sweeps, and the failsafe below. `DELETE /order` with L2 auth (see `polymarket_api.rs` cancel path).
- [x] **Consecutive-API-error failsafe** — LP tool pattern: after N consecutive CLOB API failures, cancel all open orders and halt (`PASSIVE_MAX_API_ERRORS`). Cheap, high-value safety net once gekko has resting orders.

### 🟡 Medium — market data + execution quality

- [ ] **WebSocket market data** — `marketdata` polls books via REST every 5s (`POLYMARKET_POLL_INTERVAL`); Polymarket has market + user channels at `wss://ws-subscriptions-clob.polymarket.com/ws/{market,user}`. LP tool treats WS as primary with REST reconciliation. For gordon's momentum signals, 5s polling misses moves and burns rate limit; the user channel also gives fill detection for free (feeds the lifecycle item above).
