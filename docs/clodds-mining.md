# CloddsBot → gekko: idea-mining report

_Generated 2026-07-10 from source on disk: a local checkout of CloddsBot (clodds v1.8.0, TypeScript) vs this repo. Every item cites both the CloddsBot module it came from and the gekko file/function it would land in. No CloddsBot code is proposed for import — each item is a Go reimplementation that either emits a `StrategyProposal` or slots into breen._

**Scope assumptions (stated, then proceeded on):** gekko is YES-only, paper/sim, no leverage, breen is the sole execution authority; anything in CloddsBot that assumes direct broker access, leverage, perps, or DeFi is evaluated only for its *decision logic*, never its execution path. "Current priorities" = signal quality (BUY-coercion bias, muzzled bearish signals, random position expiry) and fault tolerance, per `bug_list.md`, `gekko_improvement_tasks.md`, and `docs/session-plan-metrics-first.md`.

## Executive summary — strongest ADOPT-NOW ideas

- **Entity-verification of semantic market matches** (CloddsBot `src/opportunity/matching.ts` `verifyMatch`): a ~150-line pure-Go check that a matched Kalshi market actually shares the news event's dates/years/thresholds/names before `processEvent` trades it. Directly attacks the hallucinated-edge / wrong-market failure mode behind the favorite-longshot losses; gekko's `MarketMatcher.Match` (`gordon/markets.go:283`) currently trusts cosine ≥ 0.5 alone.
- **Consecutive-loss + loss-velocity circuit breaker** (CloddsBot `src/execution/circuit-breaker.ts`): breen's drawdown halt is a *level* trigger; CloddsBot also trips on streaks and daily loss. Two new `RiskCaps` fields and ~30 lines in `riskGate` (`breen/tracker.go`) close the "fast bleed below the halt line" gap. Small, testable beside `riskguards_test.go`.
- **Volatility-regime size multiplier** (CloddsBot `src/risk/volatility.ts`): rolling stddev of recent closed-trade returns → regime → 1.0/0.5/0.25× entry sizing. A ~120-line breen module that implements the "graduated de-risking" your own `docs/breen-intelligence-proposal.md` Phase 2 calls for, with a simpler statistic.
- **Per-persona Brier scores** (CloddsBot `src/acp/predictions.ts`): `(confidence − outcome)²` per contributor, folded into `computePersonaStats` (`breen/account.go:385`). The inputs already exist (`ContributorProposal.Confidence` + `PersonaScore`); this is the cheapest concrete step toward the calibration phase the breen-intelligence proposal ranks as gap #2.
- **Order-book imbalance as a signal input** (CloddsBot `src/execution/index.ts` `calculateOrderbookImbalance`): bid/ask depth imbalance is the one cheap, *directional* book signal gekko doesn't compute — and unlike the current momentum/sentiment inputs it strengthens the bearish side too, feeding the bear-veto path in `breen/consensus.go`.

## ADOPT NOW

### 1. Entity-verification gate on news→market matches
1. **What:** After the embedding match picks a real Kalshi ticker, verify with cheap regex/token extraction that the news text and the market title agree on the *critical entities* — years, dates, numeric thresholds, person/team names — and shrink or reject the match on mismatch.
2. **Where in CloddsBot:** `src/opportunity/matching.ts` — `verifyMatch()` (line ~348) and `extractEntities()`: extracts `years`, `dates`, `thresholds`, `persons`, `teams`; each mismatch subtracts a confidence penalty (year −0.5, date −0.4, threshold −0.4, person −0.3) and can set `needsReview`. Used to keep semantic matches (cosine ≥ 0.85) from pairing "BTC > $100k by *Jan*" with "…by *Feb*".
3. **Mapping onto gekko:** `MarketMatcher.Match` (`gordon/markets.go:283`) returns `(ticker, title, yesBid, yesAsk, score)` on cosine ≥ `MatchThreshold` (default **0.5** — far looser than CloddsBot's 0.85) and `processEvent` (`gordon/main.go`) then overrides `contractID` with the matched ticker. Add a pure func `verifyMatch(newsText, marketTitle string) (penalty float64, warnings []string)` in `gordon/markets.go`; in `processEvent`, apply it right after the match and before the `fairImplausible`/`edgeVsMarket` gates — either subtract the penalty from `matchConfidence` (which flows into `SignalInputs.MatchScore` → `compositeConfidence` → `StrategyProposal.Confidence`) or drop the match outright past a threshold. Tests beside `markets_test.go`.
4. **Why it helps:** The 2026-07-08 forensics trail (comments on `minEntryPrice`/`fairAskMaxRatio` in `gordon/main.go`) shows the losses come from the LLM "finding edge" on the wrong or mispriced market. A wrong-market match is invisible to every downstream gate — the edge check runs against the *matched* book. This is a signal-quality fix at the exact point the error enters. It also de-risks `crossVenueEdge` (`gordon/markets.go:233`), which pairs markets across venues by embedding alone.
5. **Effort:** **S** (~150–250 lines Go, regex + set comparison, no dependencies).
6. **Risk/caveat:** Kalshi *titles* are terse; extraction may find no entities, in which case the gate must be a no-op (fail-open), mirroring CloddsBot's "no entities ⇒ no penalty". Don't reuse its person/team NLP lists — date/year/threshold alone carries most of the value here.

### 2. Consecutive-loss and daily-loss circuit breaker
1. **What:** Trip a trading halt on (a) N consecutive losing closes and (b) daily realized loss ≥ $X or %NAV, with a cooldown — independent of the existing peak-drawdown halt.
2. **Where in CloddsBot:** `src/execution/circuit-breaker.ts` (`maxConsecutiveLosses: 5`, `maxLossUsd`, `maxLossPct`, `cooldownMs`, `resetTimeoutMs`, trip reasons enum); daily-loss and drawdown limits also in `src/trading/safety.ts` (`SafetyConfig.dailyLossLimit`, `maxDrawdownPct`); orchestrated as check #1–2 in `src/risk/engine.ts` `validateTrade`.
3. **Mapping onto gekko:** Extend `RiskCaps` (`breen/tracker.go:314`) with `MaxConsecutiveLosses int`, `DailyLossLimit float64`, `BreakerCooldown time.Duration`; env wiring in `breen/config.go` beside `MAX_DRAWDOWN_HALT_PCT`. `riskGate` (`breen/tracker.go:417`) already snapshots what's needed: `closedTrades` is ordered (sorted by `ClosedAtMs` in `computePersonaStats`), so a streak counter and a UTC-day realized-PnL accumulator can be maintained in `recordClosedTradeLocked` (`breen/account.go:142`) under the same lock. Mirror the new flags into `computeRiskState` (`breen/riskstate.go:35`) so gordon's pre-LLM veto (`RiskStateReader.Evaluate`, used in `gordon/main.go` `[PREGATE]`) skips LLM calls while tripped. Tests beside `riskguards_test.go`.
4. **Why it helps:** Fault tolerance for exactly the observed failure shape: run #2 lost −10.52% *without* necessarily hovering at the −10% NAV cliff at any instant — a streak/velocity trigger fires earlier than a level trigger during a correlated bleed. The gate also protects against a degenerate regression (e.g. a bad prompt change) producing many small correlated losers that never trip family/category limits.
5. **Effort:** **S** (~80–150 lines incl. tests).
6. **Risk/caveat:** SELLs/exits must keep passing (same rule as every gate: "exits only reduce exposure"). Daily boundaries need one decision (UTC vs exchange ET — recommend ET, consistent with `kalshiTZ` in `gordon/signals.go`). Don't port CloddsBot's error-rate trip limb — gekko's LLM failures already degrade to decline/fallback, not to orders.

### 3. Volatility-regime size scaling
1. **What:** Classify recent realized P&L volatility into low/normal/high/extreme via rolling stddev vs a calibrated baseline; multiply new-entry size by a per-regime factor (1.0 / 1.0 / 0.5 / 0.25), optional halt on extreme.
2. **Where in CloddsBot:** `src/risk/volatility.ts` (`createVolatilityDetector`, `regimeMultipliers`, baseline calibrated from the first full window); applied as check #9 in `src/risk/engine.ts` `validateTrade`, multiplying the Kelly/requested size.
3. **Mapping onto gekko:** New `breen/volregime.go`: keep a ring of the last ~30 `ClosedTrade.ReturnPct` values (fed from `recordClosedTradeLocked`), expose `sizeMult() float64`. Apply in `ProcessStrategyProposal` (`breen/tracker.go:599`) after `riskGate` passes and before `ExecuteOrder`, scaling `proposal.TotalSize` for BUYs only, with the multiplier logged into `BreachReason` the way the consensus bear-veto annotates (`breen/consensus.go` `"; bear-veto ×%.2f"`). Surface the current regime in the health snapshot (`breen/health.go`) and optionally `gekko:risk_state`.
4. **Why it helps:** Implements the "graduated de-risking" ramp `docs/breen-intelligence-proposal.md` Phase 2 asks for (removing the drawdown-cliff problem, gap #4) using a statistic that needs no calibration table and no Kelly inputs. Sizing down during churn directly attenuates the "keep re-entering after getting burned" loop the post-mortem documents.
5. **Effort:** **S/M** (~120–200 lines + tests; the stddev math is trivial, the care is in only scaling entries and never conflicting with the buying-power clamp in `ExecuteOrder`).
6. **Risk/caveat:** Skip CloddsBot's `low: 1.2×` boost — gekko's own guardrail doctrine ("never size up in v1", breen-intelligence proposal) says shrink-only. Trade-count-based windows behave badly when trade flow is sparse; gate behind a min-sample count like `metricsMinSamples`.

### 4. Per-persona Brier score → calibration-aware weighting
1. **What:** Score every contributor's stated confidence against the trade's binary outcome with `(conf − outcome)²`; keep a running per-persona Brier; use it to discount stated confidence where it feeds gates and consensus.
2. **Where in CloddsBot:** `src/acp/predictions.ts` — `brierContribution = Math.pow(row.probability - outcome, 2)` (line ~319), accumulated into per-agent `brierSum`/`brierScore` and used to *rank agents by forecast accuracy*, separate from P&L.
3. **Mapping onto gekko:** All inputs already persist: `ClosedTrade.PersonaScores` carries per-persona results and `ContributorProposal.Confidence` the stated conviction (`breen/tracker.go:45`, stamped by `consolidateProposals` in `breen/consensus.go:262`). Add a `Brier float64` (n₀-shrunk, like `personaWeights`' shrinkage) to `PersonaStat` in `computePersonaStats` (`breen/account.go:385`) → it flows to `gekko:persona_stats` → `PersonaScorecard.tsx` for free. Then (step 2, optional) fold it into `personaWeights` (`breen/consensus.go:317`) or the `midBandConfidence` check (`breen/tracker.go:403`): a persona with Brier worse than chance (>0.25) gets its stated confidence shrunk toward 0.5 before the mid-band gate reads it.
4. **Why it helps:** Breen-intelligence gap #2 verbatim ("nobody checks whether a persona's 0.8 historically wins more than its 0.5"), and it sharpens the exact gate (mid-band conviction) built to stop the 0.35–0.65 band that lost −$9,036. Brier is the right scoring rule for it — win-rate (current `personaWeights`) can't distinguish over-confident from well-calibrated personas. Display-only first (Phase-0 discipline), act on it after one run of data.
5. **Effort:** **S** for the metric (~60 lines in `breen/account.go` + test in `persona_stats_test.go`); **M** for wiring it into consensus/gates behind a `CALIBRATION_ENABLED`-style env.
6. **Risk/caveat:** Outcome definition matters in a system with force-exits and stops: use win/loss of the persona's own `PersonaScore.ReturnPct` (already the scorecard convention), not contract resolution, or the score punishes personas for breen's exit policy. Sample sizes are small — shrink hard, and keep the display-only period honest.

### 5. Order-book imbalance signal (directional, bear-capable)
1. **What:** Compute top-N-level bid/ask volume imbalance (`(bidVol − askVol)/(bidVol + askVol)`), with a reliability score from total volume, spread tightness, and magnitude; feed it into proposal confidence/size like momentum.
2. **Where in CloddsBot:** `src/execution/index.ts` — `calculateOrderbookImbalance` / `getOrderbookImbalance` (line ~916): signal = bullish/bearish past ±0.15 imbalance; `confidence = 0.4·volumeScore + 0.3·spreadScore + 0.3·|imbalance|`. Consumed by `src/opportunity/scoring.ts` (`scoreWithImbalance`) and as `orderbook.imbalanceScore` in the ML feature vector (`src/trading/ml-signals.ts`).
3. **Mapping onto gekko:** marketdata already snapshots books to Redis (`orderbook:<ticker>`, `AsOfMs`) and publishes `momentum:<ticker>` (`marketdata/momentum.go`; read by `readMomentum` in `gordon/signals.go:208`). Add `imbalance` to the momentum JSON in `marketdata/momentum.go` (computed from the book it already holds), add an `Imbalance float64` field to `SignalInputs` (`gordon/signals.go:28`), and a term in `compositeConfidence` (`gordon/signals.go:40`): aligned imbalance adds up to ±0.10, exactly like the sentiment term. It reaches breen through `Confidence` on the `StrategyProposal` — no breen change.
4. **Why it helps:** Signal quality with a bearish payoff: today's enrichment inputs (lexicon sentiment, trend, vol surge) are headline-driven and empirically bull-biased, part of why bear personas produced 3 orders from 1,309 LLM calls before the bearish-signal path was added. An ask-heavy book raises bear-veto conviction (`emitBearishSignal` carries `Confidence` into `weightedConviction` in `breen/consensus.go:102`) using data gekko already fetches. Also directly usable in the near-term "quant dossier" prompt block (see #6).
5. **Effort:** **S/M** (~100–180 lines across marketdata + gordon + tests).
6. **Risk/caveat:** Thin Kalshi books make imbalance noisy — keep CloddsBot's volume-scaled reliability discount, and clamp the term small (±0.10) so it nudges rather than drives. It is a *contrarian-vulnerable* signal (big asks can be one market maker); never let it bypass the edge gates.

### 6. "Quant dossier" prompt block — feature vector in the proposal prompt
1. **What:** Give the LLM the same compact numeric feature set an ML model would get — spread %, book imbalance, momentum, days-to-expiry, volume-vs-average — as a labeled block in the proposal prompt, instead of just title + bid/ask.
2. **Where in CloddsBot:** `src/trading/ml-signals.ts` `MarketFeatures` (price change/volatility/RSI, volume vs 7-day avg, `orderbook.{bidAskRatio, imbalanceScore, spreadPct, depth10Pct}`, `market.daysToExpiry`) — the curated feature list is the transferable artifact, regardless of their gradient-boosting consumer.
3. **Mapping onto gekko:** Pure prompt change in `GenerateProposal` (`gordon/rag.go:196`): extend the `LiveMarket` struct (`gordon/rag.go:186`) with the fields gordon already has in hand at call time in `processEvent` — `TrendPct`/`VolSurge` (from `readMomentum`), spread (from `realBid`/`realAsk`), time-to-expiry (from `tickerExpiry`, `gordon/signals.go:98`), imbalance once #5 lands — and render them as a "MARKET MICROSTRUCTURE" section between the live-market block and the analysis steps.
4. **Why it helps:** This was explicitly deferred in `docs/session-plan-metrics-first.md` (§4 "Quant dossier") and is the cheapest remaining lever on raw proposal quality — the post-mortems keep concluding "the remaining lever is proposal quality itself." A model told the spread is 8¢ and expiry is 3h is materially less likely to claim 15¢ of edge. This is a "prompt the LLM differently" item: near-zero code risk, high interest.
5. **Effort:** **S** (~60–100 lines, mostly prompt text + plumbing already-computed values).
6. **Risk/caveat:** Longer prompts cost latency on local Ollama (the 88%-fallback history in `gekko_improvement_tasks.md` 🔵) — keep the block ≤ ~6 short lines. A/B it per-persona via the existing registry/scorecard machinery (`gordon/personas.go`) rather than fleet-wide at once.

## EVALUATE

### 7. Dynamic fractional Kelly sizing with drawdown/streak modifiers
1. **What:** Quarter-Kelly base sizing from edge and win probability, with multiplicative adjustments: ×0.5 in drawdown, small boost on win streaks (anti-martingale), category-specific multipliers, sample-size shrink.
2. **Where in CloddsBot:** `src/trading/kelly.ts` (`DynamicKellyCalculator`, `KellyAdjustment` types: `confidence | drawdown | win_streak | volatility | category | sample_size`); consumed as check #10 in `src/risk/engine.ts`, taking `min(requestedSize, kellySize × regimeMult)`.
3. **Mapping onto gekko:** This is `docs/breen-intelligence-proposal.md` Phase 2's `edgeScalar` almost line for line — it would live where that doc says: a scalar applied in `ProcessStrategyProposal`/`ExecuteOrder` (`breen/tracker.go`) after `riskGate`, computed from calibrated win probability and entry price. CloddsBot's contribution is a worked reference for the *adjustment stack* and its clamps.
4. **Why evaluate, not adopt:** Kelly with *uncalibrated* p is garbage-in — gekko's own proposal correctly sequences calibration (idea #4) first. Also `consolidateProposals` (`breen/consensus.go:284`) already applies a 0.5–2.0× agreement multiplier; stacking a second sizer before the first is measured invites over-shrink (the 2026-07-08 funnel-flatline incident came from exactly this kind of compounding gate interaction).
5. **Effort:** **M** (~200–300 lines + careful interaction tests with consensus sizing and the buying-power clamp). Depends on: idea #4 shipped and one run of calibration data.
6. **Risk/caveat:** Skip the win-streak *boost* limb entirely (sizes up; violates the shrink-only guardrail). CloddsBot's bankroll concept maps to `pt.cash`/NAV — be explicit that Kelly fractions apply to NAV, not `MaxTotalDeployed`.

### 8. Feature/outcome collector for offline learning (Lou's missing dataset)
1. **What:** Snapshot the full feature vector at *signal time* for every proposal — including ones that were vetoed, declined, or lost consensus — then label outcomes at a fixed horizon later, producing a training/analysis table of decisions *and* counterfactuals.
2. **Where in CloddsBot:** `src/ml-pipeline/collector.ts` (`ml_training_samples` table: features JSON at signal time, `entry_price`, `outcome_direction`/`outcome_return` labeled after `HORIZON_MS`, cleanup after N days); horizon labeling decoupled from whether the trade executed.
3. **Mapping onto gekko:** Lou (`lou/main.go`, `lou/lessons.go`) analyzes only `trades.jsonl` — *executed closes*. Every `[PREGATE]`, `[EDGE]`, `[FLOOR]`, `[SKEW]`, `[DECLINE]`, and consensus-skip drop in `gordon/main.go` `processEvent` / `breen/consensus.go` `flush` vanishes from the record. Add an append-only JSONL sink (Redis list → file, like `RunExporter` in `breen/export.go`): gordon writes one line per proposal-decision with `SignalInputs`, gate outcome, and matched book; a small labeler (in `lou/`, run at analysis time) joins later marks/resolutions from the equity/mark history to answer "what did the vetoes cost/save?".
4. **Why evaluate, not adopt:** High value but only pays off through Lou's analyzers, which need new analyzer code to consume it — it's a dataset, not a behavior change. Worth a design pass in the next Lou session; the counterfactual question ("are the entry floor and pregate leaving money on the table?") is currently unanswerable, which is a real strategic blind spot given how many gates have been added by forensics.
5. **Effort:** **M** (~150 lines to emit; ~150–300 in lou to label/analyze). No external dependency.
6. **Risk/caveat:** Volume — at thousands of LLM calls/day, log the *gated* decisions, not raw events; cap and rotate like `maxClosedTrades`. Labels for never-traded proposals need a mark source at horizon; the 5-minute equity/mark snapshots bound the achievable resolution.

### 9. Implication/relationship arbitrage between related markets
1. **What:** Detect logically related market pairs — identical, `A implies B`, mutually exclusive, time-shifted (BTC>100k by Jan vs by Feb) — and flag violations of the implied probability ordering (e.g. P(A-by-Jan) > P(A-by-Feb) is a hard mispricing).
2. **Where in CloddsBot:** `src/opportunity/correlation.ts` (`CorrelationType = 'identical' | 'implies' | 'mutually_exclusive' | 'time_shifted' | 'partial'`, `impliedCorrelation` vs `expectedCorrelation`, mispricing in probability points); scored/executed via `src/opportunity/index.ts` and `scoring.ts`.
3. **Mapping onto gekko:** As a *deterministic persona*, following the weather-strategy pattern exactly: `NewWeatherStrategy` (`gordon/weather.go:73`) shows how a non-LLM strategy emits `StrategyProposal`s with its own persona identity and `Confidence`. A "relations" gordon would scan the market catalog gordon already syncs (`MarketMatcher.syncOnce`, `gordon/markets.go:92`) for time-shifted ladders within a series (trivially derivable from `tickerExpiry` + shared family via the same `SERIES-EVENT` split as breen's `contractFamily`) and emit BUYs on the dominated leg when ordering inverts by more than spread+minEdge. Breen needs zero changes — proposals flow through consensus and the gates like any persona.
4. **Why evaluate, not adopt:** The intra-series time-shifted case is clean and cheap, but breadth beyond it (cross-series "implies") needs the entity/matching hardening of idea #1 first, and the strategy only fires when such inversions actually occur on Kalshi — unknown base rate; needs a measurement pass (log candidate inversions for a run before trading them).
5. **Effort:** **M** for the time-shifted-only persona (~250–300 lines); **L** for general implication pairs.
6. **Risk/caveat:** True arbitrage wants *both* legs; YES-only gekko can only buy the cheap leg (and emit a bearish signal on the rich leg — which the consensus bear-veto can use). That halves the edge and leaves directional residual — size accordingly. Careful: strike ladders within one event are *mutually exclusive* buckets, not implications; only the time/threshold-monotone series qualify.

### 10. Feed-freshness watchdog with explicit stale/recovered states
1. **What:** A service-level monitor that tracks last-update time per feed/book, counts consecutive stale checks, emits stale/recovered events, and flips consumers into a degraded mode instead of silently serving old data.
2. **Where in CloddsBot:** `src/feeds/freshness.ts` (`FreshnessTracker`: `staleThresholdMs`, `staleCountThreshold`, polling fallback, `stale`/`recovered`/`fallbackStarted` events).
3. **Mapping onto gekko:** gekko handles staleness *reactively and locally*: `entryBookBlock` (`breen/tracker.go:572`) rejects entries on books older than `bookFreshMaxAge`, `noQuoteMarks` counts markless positions, momentum requires ≥2 samples. What's missing is the *aggregate* view: if marketdata's poller dies, breen just quietly rejects everything ("no live two-sided order book") while stops/settlements mark off increasingly stale cache. Add a freshness sweep to breen's settlement tick (`runSettlementLoop`, `breen/account.go:501`): fraction of open positions with live books, age of newest book, published into the health snapshot (`breen/health.go`) and `gekko:risk_state` — plus an explicit `[FEEDS STALE]` log/halt-entries flag past a threshold.
4. **Why evaluate, not adopt:** Pure fault-tolerance/observability win and cheap, but its value depends on how often marketdata actually degrades — worth shipping the *metric* first (Phase-0 discipline) and the halt behavior only if the metric shows real incidents.
5. **Effort:** **S/M** (~100–150 lines; the data is already in `markCache` + book `AsOfMs`).
6. **Risk/caveat:** Don't auto-liquidate on staleness (CloddsBot never does either) — stale feeds mean *unknown* prices, and the mark-honesty rules (`resolveMark`, `breen/account.go:87`) already handle valuation. Halt entries, keep exits manual.

### 11. Open-Meteo/NWS *forecast* feed for the weather strategy
1. **What:** Free forecast APIs (hourly forecasts, not just observations) as an input to weather trading.
2. **Where in CloddsBot:** `src/feeds/weather-nws/` and `src/feeds/weather-openmeteo/` (feed adapters).
3. **Mapping onto gekko:** gekko's weather gordon (`gordon/weather.go`) prices only *already-cleared* buckets from METAR observations (`SettleResolution="YES"` hint, `sourceWeather` routing in `gordon/main.go:597`). `docs/weather-phase2-forecast-bias.md` already sketches the forecast extension; CloddsBot confirms Open-Meteo/NWS as the zero-cost sources. Would land in kahuna as a new ingest (`kahuna/ingest/`) or directly in `WeatherStrategy`.
4. **Why evaluate, not adopt:** It's your existing phase-2 doc's call, not a new idea — CloddsBot just de-risks the source choice. Forecast-based pricing carries model risk the cleared-bucket strategy deliberately avoids.
5. **Effort:** **M** (new ingest + probability model + tests).
6. **Risk/caveat:** Forecast trades lose the deterministic `SettleResolution` guarantee — they must flow through the normal gates as probabilistic proposals, not settlement hints.

## Cross-cutting observations

- **Architecture validates gekko's split.** CloddsBot's `src/risk/engine.ts` runs ten *ordered, named checks* with a `CheckResult[]` audit trail per decision. Gekko's `riskGate` returns only the first failure reason. A cheap observability borrow (fits ADOPT #2's diff): accumulate all failed/passed check names into the `[RISK]` ledger reason, so post-run forensics can count *which* gates bind — today that requires log archaeology.
- **Defaults discipline matches.** CloddsBot's signal router defaults to `enabled: false, dryRun: true`; every ADOPT item above should keep gekko's identical convention (env-gated, off/neutral by default), as the risk-guard pass did.
- **What CloddsBot has that gekko structurally doesn't need:** most of its 100+ modules exist because it's a multi-tenant, multi-venue, user-facing terminal. Gekko's single-operator, single-book, one-executor design means the valuable transfers are exactly the small pure-math/gating pieces listed above — not the platform.
